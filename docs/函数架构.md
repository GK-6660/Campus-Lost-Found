# 函数架构

**状态：** 第一周冻结稿。函数名以这里为准。  
**不管什么：** 实现以 `软件设计说明书.md` 为准。本文保留作调用关系速查。打分公式见 `技术方案与架构.md` 第 10 节。  
**改法：** 先改本文件并让组长合并，再改代码。

路由函数只做三件事：读会话、查幂等、调用下面的一个服务函数。匹配规则、状态、通知不要写在路由里。

---

## 1. 调用怎么分层

```text
页面函数（A–D）
    → 前端 api 函数（只发 HTTP）
        → 路由函数（E/F/G，和路径一一对应）
            → 服务函数（真正改数据库）
```

页面不直接写 SQL，也不拼另一套字段。模型函数只返回类别和颜色，不写匹配、不改物品状态。

依赖只能往下，不能绕回去：

```text
claims  → items、match、notify
reports → items、notify
items   → tags、files、match、extract
extract → tags、files
match   → notify
scoring 不调用任何模块
auth、files、notify 不被上面反过来依赖
```

`items` 可以调用 `match.rematch_*`。`match` 自己查物品行，不调用 `items.create_item` / `update_item`。

---

## 2. 后端文件

```text
backend/app/
  api/          路由函数。E 写 auth、files、items；F 写 matches、notifications；G 写 jobs、claims、reports
  api/deps.py   从 Cookie clf_session 取当前用户
  errors.py     共用异常。E 维护，其他组只 raise
  schemas.py    字段表里的资源形状，各组共用
  auth.py
  files.py
  items.py      含状态变更
  tags.py
  extract.py
  scoring.py    纯函数
  match.py
  notify.py
  claims.py
  reports.py
  idempotency.py
```

登录和注册成功后，由 `api/auth.py` 的 `_issue_session` 写 Cookie。服务函数不接收 `Response`。

服务函数抛这些异常，路由翻译成字段表里的 HTTP 码。各组不要自己发明错误 JSON。

| 异常 | HTTP |
| --- | --- |
| `Unauthenticated` | 401 |
| `Forbidden` | 403 |
| `NotFound` | 404 |
| `VersionConflict` | 409 `version_conflict` |
| `FoundAlreadyReturned` | 409 `found_already_returned` |
| `InvalidState` | 409 `invalid_state` |
| `ValidationError` | 422 `validation_error` |

写操作的路由先调用 `idempotency.replay_if_done(user_id, request_id)`。已经做过就直接返回上次结果，不再进入服务函数。成功后调用 `idempotency.save(user_id, request_id, response)`。

## 3. 服务函数

签名里的类型是说明，不是要额外发明的字段。`User`、`Item` 就是字段表里的那些资源。

### 3.1 账号与图片（E）

| 函数 | 谁调用 | 做什么 |
| --- | --- | --- |
| `auth.register(student_no, nickname, password) -> User` | 路由 `POST /auth/register` | 写入用户，角色固定 `user` |
| `auth.login(student_no, password) -> User` | 路由 `POST /auth/login` | 密码不对抛 `Unauthenticated` |
| `auth.logout(session_id) -> None` | 路由 `POST /auth/logout` | 删会话 |
| `auth.current_user(session_id) -> User` | 所有要登录的路由 | 没有会话抛 `Unauthenticated` |
| `auth.require_admin(user) -> None` | 管理路由 | 不是管理员抛 `Forbidden` |
| `files.save_redacted_image(owner_id, data, mime) -> File` | 路由 `POST /files` | 校验类型和 5MB，只存这一张 |
| `files.read_image(file_id, viewer) -> bytes` | 路由 `GET /files/{id}` | 上传者、候选里看到这张图的失主、管理员。其他人抛 `NotFound` |
| `files.get_own_file(file_id, owner_id) -> File` | `items.create_item` | 图必须是当前用户刚上传的 |

### 3.2 物品与标签（E）

只有这个模块可以改 `items.status` 和 `items.version`。

| 函数 | 谁调用 | 做什么 |
| --- | --- | --- |
| `items.create_item(owner, payload) -> Item` | 路由 `POST /items` | 建草稿。有类别颜色则 `tags.upsert_user_tags`。不打分 |
| `items.update_item(owner, item_id, version, patch) -> Item` | 路由 `PATCH /items/{id}` | 先 `lock`。`confirm_tags=true` 时 `tags.confirm`，再 `match.on_tags_confirmed` |
| `items.publish_item(owner, item_id, version) -> Item` | 路由 `POST /items/{id}/publish` | 校验必填，`mark_open`，然后按第 4 节分支 |
| `items.close_item(owner, item_id, version) -> Item` | 路由 `POST /items/{id}/close` | `mark_closed`。之后不再匹配 |
| `items.list_mine(owner, type, status) -> list[Item]` | 路由 `GET /items` | 最多 100 条 |
| `items.get_for_viewer(viewer, item_id) -> Item` | 路由 `GET /items/{id}` | 主人或管理员，否则 `NotFound` |
| `items.lock(item_id, version) -> Item` | `update_item`、`publish_item`、`close_item`、`claims.submit_claim`、`reports.takedown` | 行锁。版本不对抛 `VersionConflict` |
| `items.mark_open(item) -> None` | `publish_item` | `status=open`，写 `expires_on` |
| `items.mark_returned_pair(lost, found) -> None` | `claims.submit_claim` | 两条都变为 `returned`，版本各 +1 |
| `items.mark_closed(item) -> None` | `close_item`、`reports.takedown` | `status=closed` |
| `tags.upsert_user_tags(item, category, color) -> None` | `create_item`、`update_item` | `source=user`，`confirmed=true` |
| `tags.confirm(item) -> None` | `update_item` | 把已有类别、颜色标成已确认 |
| `tags.write_model_tags(item, category, color) -> None` | `extract.run_extract` | `source=model`，`confirmed=false`。不写品牌 |

`to_owner_view(item)` 和 `to_public_view(item, place_code)` 也放在 `items.py`。公开投影的字段以字段表第 3.3 节为准。`match.list_matches` 调用 `to_public_view`。

### 3.3 识别（G）

| 函数 | 谁调用 | 做什么 |
| --- | --- | --- |
| `extract.enqueue(item) -> Job` | `items.publish_item` | 无密钥则任务直接 `failed` / `no_model`。有密钥则后台调用 `run_extract` |
| `extract.run_extract(job_id) -> None` | `enqueue` 的后台任务 | 读涂黑图，调用 `extract_labels`，成功则 `tags.write_model_tags` |
| `extract.extract_labels(image_bytes) -> category, color` | `run_extract` | 超时 20 秒。不在词表里就当 `unknown`。不返回品牌，不写理由 |
| `extract.get_job(viewer, job_id) -> Job` | 路由 `GET /jobs/{id}` | 只有物品主人 |

`extract` 不调用 `match`。匹配等到用户确认标签。

### 3.4 打分与通知（F）

`scoring` 里的函数不读数据库、不写数据库。公式见技术方案第 10 节。

| 函数 | 谁调用 | 做什么 |
| --- | --- | --- |
| `scoring.score_pair(lost, found) -> Score` | `match.rematch_*` | 汇总下面六项。`Score` 含 `score`、`reasons`、`conflicts`、`hard_conflict` |
| `scoring.score_category(a, b)` | `score_pair` | 相同 40，未知 0，明确不同 −30 |
| `scoring.score_color(a, b)` | `score_pair` | 相同或黑/灰同组 20，未知 0 |
| `scoring.score_place(found_place, visited_places, ordered)` | `score_pair` | 地点衰减，满分 15 |
| `scoring.score_time(lost_on, found_on)` | `score_pair` | 时间衰减，满分 15 |
| `scoring.score_brand(a, b)` | `score_pair` | 双方都有且相同才 5 |
| `scoring.score_keywords(lost_desc, found_desc)` | `score_pair` | 满分 5 |
| `match.rematch_for_lost(lost_id) -> None` | `items.publish_item`、`match.on_tags_confirmed` | 和所有 `open` 的他人拾获打分，写入 `matches`，再 `notify.maybe_new_match` |
| `match.rematch_for_found(found_id) -> None` | 同上 | 和所有仍 `open` 且在订阅的他人失物打分 |
| `match.on_tags_confirmed(item) -> None` | `items.update_item` | 物品已 `open` 才重跑。失物走 `rematch_for_lost`，拾获走 `rematch_for_found` |
| `match.list_matches(owner, item_id) -> list[Match]` | 路由 `GET /items/{id}/matches` | `score >= 40`，最多 5 条，对方用公开投影 |
| `match.suppress_found(found_id) -> None` | `claims.submit_claim` | 这条拾获不再出现在别人的候选里 |
| `notify.maybe_new_match(...) -> None` | `rematch_*` | 仅当分数 ≥ 60、类别不是硬冲突、失物在订阅。同一对只插一条 |
| `notify.found_returned(user_ids, lost_id, found_id) -> None` | `claims.submit_claim` | 通知其他正在看这条拾获的人 |
| `notify.taken_down(owner_id, item_id) -> None` | `reports.takedown` | 通知物品主人 |
| `notify.list_for(user_id) -> unread_count, list` | 路由 `GET /notifications` | 最多 100 条 |
| `notify.mark_read(user_id, notification_id) -> Notification` | 路由 `POST /notifications/{id}/read` | 只能标自己的 |

`maybe_new_match` 的参数：`user_id`、`lost_id`、`found_id`、`score`、`hard_conflict`、`subscribed`、`title`、`body`。

### 3.5 找回与下架（G）

| 函数 | 谁调用 | 做什么 |
| --- | --- | --- |
| `claims.submit_claim(user, lost_id, found_id, result) -> Claim` | 路由 `POST /claims` | 见第 4.4 节。同一事务里改状态 |
| `claims.list_mine(user) -> list[Claim]` | 路由 `GET /claims/mine` | |
| `reports.create(user, item_id, reason) -> Report` | 路由 `POST /reports` | 不能举报自己的 |
| `reports.list_open(admin) -> list[Report]` | 路由 `GET /admin/reports` | 先 `require_admin` |
| `reports.takedown(admin, item_id, version, reason) -> Item` | 路由 `POST /admin/items/{id}/takedown` | `items.lock`，`items.mark_closed`，关掉相关举报，`notify.taken_down` |

## 4. 五条调用链

### 4.1 发布失物

```text
publish_item
  → items.lock
  → items.mark_open
  → match.rematch_for_lost
       → scoring.score_pair
       → 写入 matches
       → notify.maybe_new_match
```

### 4.2 发布带图、标签还空着的拾获

```text
publish_item
  → items.lock
  → items.mark_open
  → extract.enqueue
       → extract.run_extract
            → files 读图
            → extract.extract_labels
            → tags.write_model_tags
```

这里不调用 `match`。

### 4.3 用户确认标签

```text
update_item
  → items.lock
  → tags.confirm
  → match.on_tags_confirmed
       → match.rematch_for_found 或 rematch_for_lost
            → notify.maybe_new_match
```

手填类别颜色后再发布、标签已经确认的拾获，走 4.1 的形状：`publish_item` 直接 `rematch_for_found`，不建识别任务。

### 4.4 失主点已找回

```text
submit_claim(result=returned)
  → items.lock(失物)
  → items.lock(拾获)
  → items.mark_returned_pair
  → match.suppress_found
  → notify.found_returned
```

`result=not_found` 只插入一条 `Claim`，不调用 `mark_returned_pair`，两条物品保持 `open`。

### 4.5 管理员下架

```text
takedown
  → auth.require_admin
  → items.lock
  → items.mark_closed
  → 关闭相关举报
  → notify.taken_down
```

## 5. 前端函数

```text
frontend/src/api/client.ts          A  request
frontend/src/api/auth.ts            A  loadMe、login
frontend/src/api/notifications.ts   A  loadNotifications
frontend/src/api/files.ts           B  uploadFile
frontend/src/api/items.ts           B  createItem、updateItem、publishItem、confirmTags
frontend/src/api/jobs.ts            B  pollJob
frontend/src/features/redact.ts     B  redactImage
frontend/src/api/matches.ts         C  loadMatches
frontend/src/api/claims.ts          C  submitClaim
frontend/src/api/admin.ts           D  loadReports、takedown
```

前端函数只组请求和画界面。权限判断以接口返回为准。

| 组 | 函数 | 调用的路径 |
| --- | --- | --- |
| A | `api.request(path, options)` | 所有请求。带 Cookie，解析 `error.code` |
| A | `loadMe()` | `GET /auth/me` |
| A | `login(student_no, password)` | `POST /auth/login` |
| A | `loadNotifications()` | `GET /notifications`。铃铛用 `unread_count` |
| B | `redactImage(file, strokes) -> Blob` | 不发请求。按真实像素导出涂黑图 |
| B | `uploadFile(blob) -> image_id` | `POST /files` |
| B | `createItem(payload)` | `POST /items` |
| B | `updateItem(id, version, patch)` | `PATCH /items/{id}` |
| B | `publishItem(id, version)` | `POST /items/{id}/publish` |
| B | `pollJob(job_id)` | 每 2 秒 `GET /jobs/{id}`，直到 `succeeded` 或 `failed` |
| B | `confirmTags(id, version, category, color)` | `updateItem`，并带 `confirm_tags: true` |
| C | `loadMatches(item_id)` | `GET /items/{id}/matches` |
| C | `submitClaim(lost_id, found_id, result)` | `POST /claims` |
| D | `loadReports()` | `GET /admin/reports` |
| D | `takedown(item_id, version, reason)` | `POST /admin/items/{id}/takedown` |

拾获页面的顺序固定为：`redactImage` → `uploadFile` → `createItem` → `publishItem` →（有 `job_id` 则 `pollJob`）→ `confirmTags`。

`api.request` 由 A 提供。B、C、D 调用它，不各自写一套 `fetch`。

## 6. 不要出现的调用

- 路由里直接打分、直接改 `status`、直接插通知。
- `extract_labels` 写 `matches`、`claims` 或品牌。
- `scoring.score_pair` 写数据库。
- 前端把 `role` 放进请求体当权限。
- 为交接、私密证明、管理员批准认领再加函数。这些不在字段表里。
