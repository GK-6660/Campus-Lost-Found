**文档用途：** 打分公式的推导，以及部署背景。实现以 `软件设计说明书.md` 为准。  
**项目形态：** 部署在已有服务器和域名上的可用网站，同时作为 JC2001 小组项目的 Proof-of-Concept。  
**版本：** 2026-09-16（吸收组内建议：匹配订阅、时间/地点衰减、可解释理由）

失主自己标记已找回或没找到，管理员只下架。本文里的交接、私密证明、管理员批准认领不再实现。

## 0. 组内新建议怎么用

组员提出的方向大部分是对的，但不必全部做成必做。取舍如下。

| 建议 | 结论 | 原因 |
| --- | --- | --- |
| 没匹配到时持续关注新拾获，再匹配一次 | **必做**，做成匹配订阅 | 本来就要做；不要叫“监控”，报告和界面都用“订阅 / 持续匹配” |
| 匹配成功后通知失主 | **必做，只用站内信** | 没有通知，订阅就仍是翻列表；邮件/短信不上，避免 SMTP、退信和隐私 |
| 时间衰减 + 地点衰减 | **必做**，写进打分公式 | 替换原来的“地点相同 +15、时间有交集 +15”；数学简单，报告里好讲设计 |
| 可解释匹配（告诉用户为什么像） | **必做** | 候选必须带分项理由；**不要写成“匹配度 87% = 这是你的东西”** |
| 用模型看照片的颜色和类别 | **必做：模型抽标签，规则打分** | 模型读出类别/颜色；不直接宣布匹配。失败必须手填。图对图才是增强 |
| 校园地图 / 热力图 | **增强，非必做** | 演示好看，但不挡住闭环；登记地点仍用楼栋下拉，不做地图选点 |

不要采用的说法：后台一直轮询“监控失主”、把衰减分数当成归属概率、第一期就接邮件网关。

## 1. 我们要做成什么

做一个面向校园的失物找回网站。学生用浏览器打开域名即可使用，手机和电脑都能完成主要操作。

系统要解决的不是“再做一个发帖板”，而是四条实际问题：

1. 丢东西的人不知道该去哪翻、该找谁问。
2. 捡到东西的人发了照片，对不上当时还没登记、或当时没匹配上的失主。
3. 公开信息太细时，别人可能照着描述冒领。
4. 用户看到一个分数，却不知道系统为什么觉得像。

产品原则：

- 智能只负责找出值得核对的候选，不宣布“这就是你的东西”。
- 认领必须经过审核；公开特征和私密证明分开。
- 模型或识别失败时，手填仍能发布、匹配、认领。
- 先发失物、后发拾获时，系统会重跑匹配并用站内信通知，而不是让失主反复刷列表。
- 这是能给同学用的网站，但不是生产级平台：不做集群、不做消息中间件、不上向量检索中台。

## 2. 用户、场景、成功标准

### 2.1 角色

| 角色 | 谁 | 能做什么 |
| --- | --- | --- |
| 普通用户 | 学生（同一人可既是失主也是拾到者） | 注册登录、发布失物、发布拾获、查看候选和理由、申请认领、开关匹配订阅、看站内信 |
| 管理员 | 小组指定账号，后续可给学生会/宿管试用 | 看待审核认领、查看私密证明、通过或驳回、确认交接、看很浅的统计 |
| 访客 | 未登录 | 只看到项目说明和登录/注册，**没有公开帖子、不能翻库** |

第一期默认一个校区、一套地点词表。不做多租户。

### 2.2 主路径（网站上必须能走通）

1. 失主登记：类别、颜色、时间、**可能丢失/当天去过的楼栋（可多选、可排序）**、描述，可选旧照。发布后默认开启匹配订阅。
2. 拾到者在发现点拍照上传：地点、时间、可选描述。**系统调用模型抽出类别和颜色，用户可改。** 默认原位留下，没有后续义务。
3. 系统用这些标签 + 失主路线/时间打分，生成最多 5 条候选，并写明为什么像、哪里冲突。
4. 失主看到候选后可标记“这像我的”并去该地点寻找。
5. 找到则标记已找回。管理员处理滥用和争议，不保管实物。
6. 同一条拾获记录上的有效主张最多一条，避免状态被刷乱。

**订阅路径（答辩要单独演示）：** 失主先发布且当时没有合格候选 → 另一人稍后上传拾获 → 系统对所有仍为 `open` 的失物重跑匹配 → 达到通知阈值则给失主写站内信 → 失主打开铃铛看到新候选和理由。用户可关闭订阅。

重跑对象是**所有仍开放的失物**，不只是“完全没匹配到的”。已经有弱候选的失主，也可能因为新拾获而得到更好结果。通知则更严：只在出现**新的、过阈值的候选**时发送，同一失物–拾获对不重复提醒。

### 2.3 怎样算“可用”

- 用域名 HTTPS 打开，注册后能独立完成主路径，不需要开发者改数据库。
- 手机浏览器可以填表、上传图、看候选理由、提交认领、看站内信。
- 识别服务不可用时，页面明确提示，并允许手填继续。
- 刷新、重复点击、断网重试，不会把同一条登记发两次，也不会把同一件物品批给两个人。
- 先发失物、后发拾获时，失主能靠站内信知道有新候选。

## 3. 范围

### 3.1 必须交付

- 注册 / 登录 / 退出；角色：用户、管理员
- 拾获照片：发布前由上传者在浏览器里涂掉姓名、学号、独特图案、码数或序列号；只上传并保存涂过的图。模型只看这张图，抽出类别和颜色，写入可编辑标签卡，用户确认后参与打分
- 规则匹配：用这些类别、颜色，加上失主路线、时间；返回 Top 5 和理由
- 可解释匹配：每条候选带分项理由；分数用于排序，不是归属概率
- 匹配订阅 + 站内信
- 认领/已找回状态；管理员处理滥用
- 响应式网页；HTTPS 部署到现有域名
- **模型失败或无 Key 时必须能手填**，闭环不能断
- 关键路径测试：权限、重复提交、并发主张、通知去重、无模型时可手填匹配

### 3.2 有时间再做（每项可单独演示）

- 失主有旧照时，用图搜图做补充（非必须）
- 管理端浅统计
- 校园楼栋/路线可视化
- 使用说明页

### 3.3 明确不做

- 独立 App、小程序
- 登记时在地图上点选地点（地点仍用楼栋下拉）
- LangGraph / 多轮 Agent 追问
- 向量数据库、多路语义融合；第一期不以图对图当主检索（图对图是增强）
- Redis、Celery、Kafka、SSE
- 短信、邮件网关、企业微信机器人、即时聊天室
- 多校区 SaaS、复杂组织权限
- 把匹配分数说成归属概率
- 保存未涂挡的原图；用模型自动判断或自动打码；用衣物图案做图对图核对

地点用校区楼栋枚举加备注。时间用日期 + 时段（上午 / 下午 / 晚上）。楼栋的近似经纬度放在配置文件里，只供衰减公式和可选地图使用，不向用户要 GPS。

## 4. 总体架构

网站是浏览器访问的 B/S 系统。后端一个 API 进程，智能能力是后端里的两个模块，不是独立 Worker 集群。

```text
学生手机 / 电脑浏览器
        │  HTTPS
        ▼
     已有域名
        │
        ▼
   Nginx（反向代理 + 静态资源 + TLS）
        │
        ├── /            → React 构建产物
        └── /api/v1      → FastAPI
                            ├── 账号与权限
                            ├── 物品与图片
                            ├── 特征提取（可选，失败则手填）
                            ├── 规则匹配（含时间/地点衰减与理由）
                            ├── 匹配订阅 / 重跑 / 站内信
                            └── 认领状态机
                                │
                                ├── PostgreSQL
                                └── uploads/
```

同步接口处理登录、登记、查询、认领。发布拾获后在同一请求内或 `BackgroundTasks` 里重跑匹配并写通知。前端进入页面时拉一次通知列表，不做 SSE、不上消息队列。

### 4.1 为什么这样拆

| 部分 | 职责 | 不负责 |
| --- | --- | --- |
| 前端 | 收集输入、展示候选理由、站内信铃铛、提交认领 | 权限真相、匹配算法、审核决定 |
| API | 身份、校验、状态机、事务、字段裁剪 | 在模型里“记住”数据库 |
| 提取模块 | 把图片/描述变成词表内标签，供用户确认 | 发布、认领、改状态 |
| 匹配模块 | 过滤、衰减打分、生成理由、重跑订阅 | 宣布所有权；发邮件 |
| 数据库 | 保存事实、用约束保证并发与通知去重 |  |

## 5. 部署架构（已有服务器与域名）

不新买云平台、不上 Kubernetes。在现有机器上用 Docker Compose 跑一套服务，域名解析到该机器，由 Nginx 终止 TLS。

```text
Internet → 已有域名 → Nginx:443
   /        → frontend 静态文件
   /api     → FastAPI
Docker Compose: backend, PostgreSQL
磁盘: certs, uploads, postgres-data
配置: locations.json（楼栋名称 + 近似坐标，不进密钥）
```

### 5.1 上线约定

- 公网只开放 80/443；PostgreSQL 不绑定公网。
- 环境变量放服务器 `.env`，不进 Git。
- CORS 只允许本站域名。
- 照片只有涂过的那一张，经登录后的接口给发布者和被匹配到的失主。没有原图可供管理员打开。
- 上传仅 jpeg/png/webp，建议 5MB，校验文件头。
- 每日 dump 数据库和 `uploads/`；课设不做异地多活。
- 小组指定一人管服务器权限。

### 5.2 和“课设 PoC”的关系

把 PoC 放到真域名上，方便试用和答辩，并不增加微服务。User Manual 写清域名、测试账号、管理员账号，以及“先发失物再发拾获看站内信”的演示步骤。

## 6. 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 前端 | React + TypeScript | 页面多，3–4 人可并行 |
| UI | Ant Design | 表单、管理端、通知铃铛 |
| 后端 | FastAPI + Pydantic + SQLAlchemy | 接口与字段校验清楚 |
| 数据库 | PostgreSQL | 事务、部分唯一索引 |
| 迁移 | Alembic | 多人改表必须有版本 |
| 鉴权 | HTTP-only Cookie Session（或全组统一的 JWT） | 网站优先 Cookie |
| 部署 | Docker Compose + Nginx + 已有域名 | 一台服务器可给同学用 |
| 智能 | 拾获图抽类别/颜色（必须）；失败手填 | 读照片，不直接打匹配分 |
| 地图（增强） | Leaflet + 校园楼栋静态坐标 | 不上商业地图密钥也能量产演示 |

全站只能有一套前端框架。

## 7. 功能模块

```text
frontend
  账号与布局（含通知铃铛）
  失物 / 拾获登记
  候选与认领（展示分项理由）
  管理审核
  楼栋分布图（增强）

backend
  auth          注册登录、当前用户、角色
  items         草稿、发布、版本、公开投影、订阅开关
  files         上传、公开/私密访问
  extract       拾获图抽类别/颜色、jobs（失败手填）
  match         过滤、衰减打分、理由、重跑
  claims        申请、审核、交接、并发
  notify        站内信写入与去重
```

HTTP API 和内部调用走同一套领域服务。模型不能直接改库。

## 8. 核心业务流程

### 8.1 物品状态

`draft` → `open` → `reserved` → `returned`  
也可到 `closed`（第一期可只做用户撤回）。

### 8.2 认领状态

`submitted` → `approved` / `rejected` / `cancelled`

审核通过时，同一数据库事务内：申请变为 `approved`，拾获物变为 `reserved`，其他进行中申请变为 `rejected`，写审核记录与站内信。部分唯一索引保证同一拾获物最多一条 `approved`。获批后才向该失主返回 `pickup_method` 和 `pickup_note`。

### 8.2.1 平台不保管实物（已定）

我们只做信息平台。校园没有统一前台，也不能假定同学会把东西送到保管点。

拾获默认：`left_in_place`——在发现点拍照上传，东西留在原位。捡到的人没有后续义务。

失主收到匹配后，按地点和照片自己去找。系统不保证物品还在；照片记录的是当时的现场。

| 取值 | 含义 | 何时用 |
| --- | --- | --- |
| `left_in_place`（默认） | 原位拍照后离开 | 主路径 |
| `finder_hold` | 拾到者愿意暂时拿着，并留下通过后才可见的联系方式 | 可选，不默认 |
| `handed_over` | 已自行交给别人（极少用） | 可选 |

不做：组内仓库、假想前台、取件码发货、带回家再接头、对话系统。

认领仍保留，用于“这条拾获由谁主张去找/已找回”，避免状态被多人乱点。管理员处理滥用，不经手物品。

### 8.3 匹配订阅（新拾获如何打到旧失主）

不要做独立“监控进程”。发布接口写完拾获记录后调用一次 `rematch_open_lost_items(new_found_id)`。

```text
拾获发布成功
    → 对所有 status=open 且 subscribe=true 的失物重新打分
    → 更新 matches
    → 若某条新候选 score ≥ 通知阈值，且该（失物, 拾获）尚未通知过
    → 插入 notifications（站内信）
    → 失主下次打开网站看到铃铛未读数
```

约定：

- 失物发布时 `subscribe_matches` 默认为 true，用户可关。
- 通知阈值严于展示阈值。例如详情页可看到 40 分以上的候选，站内信只发 60 分以上且类别未硬冲突的。
- 去重键：`(user_id, lost_item_id, found_item_id, type=new_match)` 唯一。
- 物品已 `reserved` / `returned` / `closed` 的失物不再重跑、不再通知。
- 同一请求内重跑即可。校园数据量下几十到几百条 `open` 记录可以接受。

### 8.4 时序（认领）

```text
失主前端          API              PostgreSQL
  | 提交认领+证明     |                 |
  |----------------->| 校验后写入 claims |
  |                  |                 |
管理员              | BEGIN 锁物品行    |
  | 通过             | 再检查状态       |
  |                  | 更新 claim/item  |
  | 已预留           | COMMIT          |
```

## 9. 数据模型

| 表 | 内容 |
| --- | --- |
| `users` | 邮箱或学号、密码哈希、角色、昵称 |
| `items` | 失物含 `visited_places`（有序楼栋列表）；拾获含单个 `found_place`；状态、类别颜色等；版本；订阅 |
| `item_images` | 路径、MIME、是否公开、所属物品 |
| `item_tags` | 标准标签、来源 `user`/`model`、是否已确认 |
| `matches` | 失物 id、拾获 id、总分、分项 JSON、理由 JSON、生成时间 |
| `claims` | 申请人、目标拾获物、关联失物、证明、状态、审核意见 |
| `notifications` | 用户、类型、已读、关联失物/拾获、创建时间 |
| `jobs` | 可选；识别任务状态 |

配置文件 `deploy/locations.json`（不是业务表）：楼栋代码、显示名、近似纬度、经度。上线前按本校区填写。

约束：

- 密码只存哈希。
- `items.version` 乐观锁。
- 写操作带 `request_id`。
- `notifications` 对“新匹配”类型做唯一约束，防止重跑重复提醒。
- 列表接口按角色裁剪字段。

## 10.0 匹配怎么串起来（先读这段）

拾获照片是主输入，但**模型不直接宣布匹配结果**。

```text
拾获照片 → 模型抽出类别、颜色（词表内）→ 用户可改
失主表单 → 类别、颜色、去过的楼、时间
            ↓
同一套规则打分（类别 / 颜色 / 路径 / 时间）→ Top 5 + 理由
```

模型挂了就手填类别颜色，打分逻辑不变。这才是“主要用模型看照片的颜色和类别”，同时又不会变成黑盒 87%。

图对图（两张照片直接比）是增强，不是第一期必须。

---

不做向量库。输入一个已发布物品，输出最多 5 条候选，每条都带分项和人能读的理由。

**过滤：** 类型相反；状态 `open`；不是自己的登记。

**总分（满分 100，第一期写死，报告说明可调）：**

| 信号 | 满分 | 计算 |
| --- | --- | --- |
| 类别 | 40 | 相同 40；未知 0；明确不同 −30 且通常不通知 |
| 颜色 | 20 | 相同或同组（黑/深黑）20；未知 0 |
| 地点 / 路径 | 15 | 见 10.2 |
| 时间衰减 | 15 | 见下式 |
| 品牌 | 5 | 双方都有且相同才加 |
| 描述关键词 | 5 | 简单分词 / 包含 |

缺照片不扣成零。硬冲突（类别明确不同）可以仍出现在详情页的低分列表，但**不发站内信**。

### 10.1 时间衰减

取失物日期与拾获日期的相差天数 Δt（只取日期，时段用于并列时的微调，第一期可以忽略时段以保持简单）。

线性衰减，便于在报告里推导和画图：

```text
S_time = 15 × max(0, 1 − Δt / 7)
```

同一天为 15，相差 7 天及以上为 0。拾获日期早于丢失日期时，Δt 仍用绝对值，但理由里标明“时间顺序存疑”，该项不加满（乘 0.5）。

若报告想写指数形式，可并列给出等价写法 `15 × exp(−Δt / 3)`，实现仍以线性为准，避免两套分数。

### 10.2 地点：去过的地方 + 路径可能性

失主不确定掉在哪一栋时，可多选当天**可能丢失/去过的楼栋**，并可勾选“按当天顺序”。拾到者只选拍照的那一栋。不采集 GPS，不用用户画轨迹。

楼栋中心点仍来自 `locations.json`。

记拾获点为 F，失主地点集合为 V。若勾选了顺序，V 为有序列表 P1, P2, … Pn。

1. 到各停靠点的最短距离  
   `d_stop = min 距离(F, Pi)`  
2. 若有顺序且 n≥2，再算 F 到每段 Pi→Pi+1 线段的距离，取最小 `d_seg`  
3. `d = min(d_stop, d_seg)`（无顺序则只用 d_stop）

```text
S_place = 15 × max(0, 1 − d / 800)
```

解释文案：

- F 就是某个 Pi：`出现在你去过的一食堂`
- F 靠近某段路径、但不是停靠点：`在图书馆到一食堂沿途附近约 150 米`
- d≥800：地点项 0 分，不因此否掉整条（类别颜色仍可匹配）

只选了一栋时，退化为原来的单点衰减。配置缺失时：F 落在集合内满分，否则 0。

这就是报告里可写的“路径可能性匹配”：不是追踪手机，而是用校园楼栋图上的点与折线做几何接近。地图画出路线是增强，第一期多选列表即可。

### 10.3 可解释输出（报告可写 Explainable Matching）

每条候选返回结构化理由，前端直接渲染，禁止模型再“编一段解释”。

```json
{
  "score": 72,
  "score_max": 100,
  "notify": true,
  "reasons": [
    {"code": "category", "points": 40, "text": "类别相同：耳机"},
    {"code": "color", "points": 20, "text": "颜色相同：黑色"},
    {"code": "place", "points": 15, "text": "出现在你去过的一食堂（当天路线：图书馆→教学楼A→一食堂）"},
    {"code": "time", "points": 13, "text": "时间相差 1 天"}
  ],
  "conflicts": []
}
```

界面文案必须类似：

> 匹配分 72 / 100，仅用于排序，不是“这件东西属于你”的概率。  
> 原因：类别相同（耳机）；颜色相同（黑色）；出现在你去过的一食堂；时间相差 1 天。

不要展示“匹配度 87%”。百分号会让用户以为是归属把握。技术报告里把这一点写成设计决策：可解释性针对**特征符合程度**，所有权仍走认领审核。

### 10.4 通知阈值

展示：总分 ≥ 40 可出现在候选页。  
通知：总分 ≥ 60，且类别不是硬冲突，且订阅开启。  
线索过少（无类别且颜色/地点/品牌都缺）允许发布，候选页提示不准，默认不发站内信。

## 11. 照片识别（主路径，必须能降级）

拾获上传后必须走一次抽标签：类别、颜色落入词表。用户确认后才打分。模型只读涂过的图。

```text
浏览器内按类别提示并涂黑 → 只上传涂过的图 → 保存这一张
        → job=processing → 一次视觉/语言模型（约 20 秒超时）
        → 成功：tags(source=model, confirmed=false)
        → 失败：job=failed，表单手填
用户确认 → confirmed=true → 触发匹配
```

证件、书、衣物、带序列号的电子产品在涂黑前显示说明：涂掉姓名、学号、独特图案、码数、序列号。类别只决定提示文案，不代替上传者涂黑。原图不写盘，也不发给模型服务。

模型不得填写认领证明，不得猜测品牌，不得生成匹配理由（理由由打分模块写模板）。无 API Key 时全站仍可手填运行，答辩要能演示这条降级。

## 13. 质量属性

| 项 | 课设可验收的目标 |
| --- | --- |
| 可用性 | 核心路径在手机和桌面可完成；站内信可发现新候选 |
| 安全性 | 鉴权、角色裁剪、私密文件不公开、上传类型限制 |
| 可靠性 | 模型失败可降级；重复 `request_id` 不重复写入；并发认领只有一个通过；通知去重 |
| 可维护性 | 单仓、衰减公式和词表集中配置、Alembic 迁移 |
| 可解释性 | 候选理由与分项分数一致，可用测试断言文案含类别/地点/时间 |
| 性能 | 校园数据量级下发布后重跑秒级完成 |
| 可部署性 | 现有域名 HTTPS 可访问 |

自动化测试至少五条：

1. 未登录不能审认领；普通用户读不到他人证明
2. 同一 `request_id` 发布两次只有一条记录
3. 两个用户同时认领，只有一条 `approved`
4. 无模型密钥时手填仍能匹配
5. 先发失物再发高分拾获，产生一条站内信；再发同一拾获不重复通知

## 16. 风险与对策

| 风险 | 对策 |
| --- | --- |
